# Сценарий практического занятия — 75 минут

## Результат занятия

Студенты умеют получать сценарии из требований, выбирать границы и недопустимые
значения, разделять независимые условия, проверять их сочетания и оценивать,
замечает ли набор тестов изменение поведения. Главный тезис:
**зелёный результат относится только к проверенным сценариям**.

## Подготовка до занятия

1. Установите зависимости в обеих версиях, проверьте запуск по README.
2. Прочитайте BUGS.md. Выполните `npm run test:student` из `instructor/`:
   восемь тестов B1–B8 должны упасть, два стартовых — пройти.
3. Раздайте только `student/`. Попросите установить зависимости заранее.
4. Откройте `student/` как отдельный проект. На общем экране сначала только
   требования и стартовые тесты. Инструкторский ответ держите в отдельном окне.
5. Подготовьте доску: «вход → ожидание → правило → результат». Рассадите студентов
   по парам. Автор сценария объясняет его, напарник пробует найти пробел.

Все команды ниже выполняются **из `student/`**, кроме явно отмеченного этапа
мутаций. В начале каждого нового тестового файла нужны импорты:

```js
import { expect, test } from 'vitest';
import { calculateDelivery } from '../src/calculateDelivery.js';
```

Примеры ниже — шпаргалка ведущего, не раздатка. Перед показом каждого примера
дайте аудитории 30–60 секунд предложить данные и ожидание. Если студенты предложили
другой подходящий пример, используйте его. Не показывайте сразу весь набор ответов.

| Время | Фокус | Наблюдаемый результат |
| --- | --- | --- |
| 0–10 | Запуск и чтение двух примеров | Два зелёных теста, список непроверенных правил |
| 10–25 | Сценарии и границы | Таблица собственных сценариев, первый красный тест |
| 25–45 | Тест → ошибка → исправление | Проверены B1, B2, B4, B5, B7 |
| 45–60 | Таблицы test.each() | Проверены B3, B6, B8, обсуждены сочетания |
| 60–70 | Ручная мутация | Стартовые тесты её пропускают, расширенные обнаруживают |
| 70–75 | Обобщение и вопросы | Каждый предлагает ещё один сценарий |

## 0–10 минут. Два зелёных теста

**Объяснить.** Тест состоит из подготовки данных, вызова и проверки результата.
Пройденные примеры не равны проверке всех требований. Ожидания берём из README,
а не из того, что функция уже возвращает.

**Открыть и показать.** `README.md` — бизнес-правила; затем `test/start.test.js`.
Пока не показывайте тело функции. Запустите:

```sh
npm test
```

**Спросить.** «Что именно доказали эти два примера? Проверяли ли мы Premium?
Чем 5000 отличается от точного порога? Что вы пока не готовы утверждать?»

**Тест вместе.** На 5–8-й минуте разберите и заново наберите тело первого теста,
сохранив существующее имя и второй тест. Новых тестов на этом шаге не добавляйте:

```js
expect(calculateDelivery({
  total: 1000,
  isPremium: false,
  deliveryType: 'standard',
  promoCode: null,
})).toBe(350);
```

**Ожидаемый результат.** Ровно два теста зелёные. К 10-й минуте на доске есть
хотя бы три непроверенных правила, предложенных студентами.

**Объяснение ошибки.** Ошибка пока не найдена: имеющихся наблюдений мало.
Не заявляйте, что функция работает целиком. При технических трудностях с установкой
дайте студенту присоединиться к соседней паре и продолжайте по расписанию.

## 10–25 минут. Границы, группы значений и негативные сценарии

**Объяснить.** Разбейте данные на группы с одинаковым ожидаемым поведением.
Граница — место изменения правила. Отдельно рассмотрите недопустимые значения
и взаимодействие условий. Дробные суммы допустимы, поэтому соседями границы
могут быть не только целые числа.

**Открыть и показать.** `TASKS.md`, пустую таблицу сценариев. На 10–14-й минуте
каждая пара заполняет строки самостоятельно. На 14–20-й минуте соберите варианты
и попросите обосновать ожидания. На 20–22-й выберите один новый сценарий.

**Спросить.** «Какие значения находятся по обе стороны порога? Что означает
слово “включительно”? Чем отсутствие суммы отличается от нуля? Достаточно ли
проверить каждую скидку отдельно? Какой класс ошибки обещан?»

**Тест вместе.** На 22–25-й минуте создайте `test/calculateDelivery.test.js`
с импортами и согласованной проверкой точного порога:

```js
test('ровно 3000: стандартная доставка бесплатна', () => {
  expect(calculateDelivery({
    total: 3000,
    isPremium: false,
    deliveryType: 'standard',
    promoCode: null,
  })).toBe(0);
});
```

**Ожидаемый результат.** Новый тест красный: ожидали 0, получили 350; два старых
по-прежнему зелёные. Зафиксируйте ожидание до запуска. Исправление оставьте
на следующий этап.

**Объяснение ошибки.** Пороговый пример различает `>` и `>=`, а пример с 5000
не различает. Это B1. Само падение ещё нужно сверить с текстом требования.

## 25–45 минут. Находим и исправляем по одной ошибке

**Объяснить.** Сначала воспроизводящий тест, затем минимальная правка, затем весь
набор. При проверке отдельной льготы остальные выключаем. Для приоритета правил
сознательно включаем конфликтующие условия. Класс исключения — часть контракта.

**Открыть и показать.** `test/calculateDelivery.test.js` рядом с
`src/calculateDelivery.js`. Показывайте только обсуждаемую ветку. Запускайте
`npm test` после каждой правки или держите `npm run test:watch`.

**Спросить.** «Может ли другой параметр сделать этот тест зелёным? К какой ветке
мы не дошли из-за раннего return? Почему проверка “выбросилось что угодно” слабее,
чем проверка обещанного класса ошибки?»

**Тесты вместе и распределение времени.**

25–28: исправьте найденную границу на `total >= 3000`, покажите зелёный набор.

28–32: попросите сценарий Premium без других льгот, затем напишите:

```js
test('Premium без других льгот', () => {
  expect(calculateDelivery({ total: 1000, isPremium: true })).toBe(0);
});
```

Ожидали 0, получили 350. Спросите, совпадают ли типы у `true` и `'true'`.
Замените сравнение на `isPremium === true` — B2.

32–37: сначала спросите ожидаемую цену экспресса со всеми льготами:

```js
test('экспресс сохраняет цену при всех льготах', () => {
  expect(calculateDelivery({
    total: 5000,
    isPremium: true,
    deliveryType: 'express',
    promoCode: 'FREESHIP',
  })).toBe(700);
});
```

Ожидали 700, получили 0. Переместите обработку экспресса выше льгот,
но оставьте её **после проверки суммы** — B4. Сразу проверьте весь набор.
Попросите предложить отдельные примеры экспресса только с одной льготой.

37–41: обсудите допустимый нулевой заказ:

```js
test('нулевой заказ допустим', () => {
  expect(calculateDelivery({ total: 0 })).toBe(350);
});
```

Получили `TypeError` вместо 350. Удалите `!total` из первой проверки,
пока оставив `!Number.isFinite(Number(total))` — B5. Так следующее занятие
по таблицам самостоятельно обнаружит проблему преобразования типов.

41–45: спросите, чем неверный тип отличается от значения вне диапазона:

```js
test('отрицательная сумма нарушает диапазон', () => {
  expect(() => calculateDelivery({ total: -1 })).toThrow(RangeError);
});
```

Получили `TypeError` вместо `RangeError`. Замените класс исключения в ветке
`total < 0` — B7. Покажите, почему обёртка `() => ...` нужна для `toThrow`.

**Ожидаемый результат.** Все написанные к этому моменту проверки зелёные после
пяти исправлений: B1, B2, B4, B5, B7. Не утверждайте, что ошибок больше нет.
На доске у каждой ошибки есть вход, ожидаемое и фактическое поведение.

**Объяснение найденных ошибок.** Привязывайте каждую к правилу, а не к номеру
строки: включение границы, boolean-статус, приоритет экспресса, допустимость нуля,
класс ошибки диапазона. Если студенты самостоятельно исправили больше, примите
их результат; используйте следующий этап для расширения и упрощения тестов.

## 45–60 минут. Параметризация через test.each()

**Объяснить.** В таблице меняются данные и ожидания, тело проверки остаётся
одинаковым. Каждая строка — отдельный тест с понятным названием. Параметризация
экономит повторение кода, но сама по себе не выбирает хорошие данные.

**Открыть и показать.** Сначала `test/calculateDelivery.test.js` студентов.
Ведущему доступны готовые таблицы в `instructor/test/calculateDelivery.test.js`;
открывайте их только после предложений аудитории и только нужный фрагмент.

**Спросить.** «Какие значения нельзя объединить в одну группу? Остаётся ли
строка числом после преобразования? Какие варианты промокода должны отличаться?
Где проверять неизвестную доставку, чтобы скидка не обходила проверку?»

**Тесты вместе.** 45–50: пары предлагают неверные типы суммы. Запишите таблицу,
оставив как минимум одну строку, которую студенты предложили сами:

```js
test.each([
  ['числовая строка', '1000'],
  ['отсутствующая сумма', undefined],
  ['null', null],
  ['NaN', NaN],
  ['Infinity', Infinity],
  ['boolean', true],
])('%s вызывает TypeError', (_label, total) => {
  expect(() => calculateDelivery({ total })).toThrow(TypeError);
});
```

Часть строк красная: преобразование принимает неподходящие типы — B6.
Замените проверку на `typeof total !== 'number' || !Number.isFinite(total)`.
Повторно запустите тест нулевой суммы: исправление не должно вернуть B5.

50–55: попросите варианты доставки и контекст со скидкой:

```js
test.each([
  [1000, 'pickup'],
  [5000, 'pickup'],
  [1000, 'Standard'],
  [1000, null],
])('сумма %s, неизвестная доставка %j', (total, deliveryType) => {
  expect(() => calculateDelivery({ total, deliveryType })).toThrow(RangeError);
});
```

Изначально исключения нет — B8. До ветки экспресса и всех льгот добавьте:

```js
if (deliveryType !== 'standard' && deliveryType !== 'express') {
  throw new RangeError('Неизвестный тип доставки');
}
```

Строка с 5000 защищает от ошибочного расположения этой проверки после скидки.

55–60: предложите сравнить точный промокод с близкими вариантами:

```js
test.each([
  ['FREESHIP', 0],
  ['freeship', 350],
  ['FreeShip', 350],
  ['FREESHIP ', 350],
  [null, 350],
])('промокод %j → %s рублей', (promoCode, expected) => {
  expect(calculateDelivery({ total: 1000, promoCode })).toBe(expected);
});
```

Другой регистр неожиданно даёт 0 — B3. Уберите `toUpperCase()`, оставьте
точное сравнение `promoCode === 'FREESHIP'`. Положительная строка защищает
от полного удаления поддержки промокода.

**Ожидаемый результат.** Таблицы выявили оставшиеся B6, B8, B3; после исправлений
написанный набор зелёный. Пары умеют объяснить каждую строку. Полную матрицу
экспресса из инструкторских тестов дайте как пример расширения после обсуждения,
не тратьте на перепечатывание циклов время занятия.

**Объяснение найденных ошибок.** Преобразование не заменяет проверку типа,
запасная ветка не заменяет валидацию, нормализация не должна менять контракт.
Если времени мало, делегируйте каждой паре одну из трёх таблиц и соберите
предложенные строки на общем экране; все три поведения обсудите устно.

## 60–70 минут. Ручная мутация условия

**Объяснить.** Мутация — небольшое намеренное изменение реализации, например
замена оператора. Если тесты падают из-за изменения поведения, они «убили» мутанта.
Если остаются зелёными, изменение «выжило»: нужно выяснить, отсутствует ли нужный
сценарий или изменение вообще не меняет наблюдаемое поведение.

**Открыть и показать.** Переключитесь в отдельный проект **`instructor/`**:
`src/calculateDelivery.js`, `test/start.test.js`, `test/regressions.test.js`.
Используем исправленную версию, чтобы исходные дефекты не скрывали эффект мутации.

**Спросить.** «Какой тест, по вашему прогнозу, упадёт от замены `>=` на `>`?
Заметят ли её два первых примера? Почему прохождение строк с 2999 и 3001
не защищает саму границу? Означает ли выживший мутант обязательный дефект тестов?»

**Тест вместе и эксперимент.** 60–62: запустите `npm test` из `instructor/` —
полный набор зелёный. 62–64: найдите тест B1 и попросите студентов самим
восстановить его ожидание; при желании повторите его в студенческом проекте:

```js
test('граница обнаруживает изменение оператора', () => {
  expect(calculateDelivery({ total: 3000 })).toBe(0);
});
```

Это уже известный сценарий: важен прогноз результата, а не новое имя теста.
В инструкторском файле оставьте существующий B1, не дублируйте его.

64–67: в **инструкторской** функции временно измените только условие:

```js
// Правильное условие:
total >= 3000 || isPremium === true || promoCode === 'FREESHIP'
// Мутация: убрать знак равенства только в первом сравнении.
total > 3000 || isPremium === true || promoCode === 'FREESHIP'
```

Последовательно выполните:

```sh
npm test -- test/start.test.js
npm test -- -t 'B1:'
npm test
```

Сначала два зелёных теста, затем B1 красный (0 против 350), в полном наборе
также падает строка стандартной доставки с суммой 3000. Мутант обнаружен.
Не используйте синтаксическую ошибку: падение парсера не демонстрирует силу ожиданий.

67–70: верните `>=`, сохраните и запустите `npm test` — всё снова зелёное.
Подчеркните, что эксперимент завершён и временная ошибка удалена.

**Ожидаемый результат.** Одна и та же небольшая ошибка проходит два стартовых
примера и не проходит расширенный набор. После восстановления исходного условия
полный набор снова проходит.

**Объяснение ошибки.** Мутация воспроизводит B1. Дополнительный тест изменил
способность набора различать две реализации. Это ручная демонстрация идеи,
а не автоматический расчёт mutation score и не доказательство полноты тестов.
Синтаксически неверный мутант и эквивалентный мутант требуют отдельного рассмотрения.

## 70–75 минут. Выводы и вопросы

**Объяснить.** Тесты сохраняют договорённости о поведении. Ценность проверки —
в сценарии и ожидании, а не в количестве строк. Напомните четыре источника
сценариев: группы значений, границы, неверные данные, сочетания правил.

**Открыть и показать.** Таблицу сценариев в `student/TASKS.md` и текущий
`test/calculateDelivery.test.js`. На 70–72-й минуте каждая пара предлагает
не показанный ведущим сценарий и называет правило.

**Спросить.** «Какой тест вы теперь написали бы первым? Что ещё может остаться
непроверенным? Почему зелёный полный набор не даёт гарантии отсутствия багов?
Как вы объясните коллеге ценность теста на конкретном примере?»

**Тест вместе.** 72–74: реализуйте один короткий сценарий аудитории. Запасной
вариант, если предложений нет, — две льготы стандартной доставки одновременно:

```js
test('Premium и промокод вместе сохраняют нулевую стоимость', () => {
  expect(calculateDelivery({
    total: 1000,
    isPremium: true,
    deliveryType: 'standard',
    promoCode: 'FREESHIP',
  })).toBe(0);
});
```

**Ожидаемый результат.** Проверка проходит на исправленной версии. Участник
объясняет, какой неправильный вариант она заметит: например, двойное вычитание
стоимости доставки с отрицательным результатом. На 74–75-й минуте ответьте
на вопросы и попросите назвать один личный вывод.

**Объяснение найденной ошибки.** Новая ошибка не обязательна: зелёный тест тоже
может защищать важное правило. Если сценарий аудитории обнаружил баг, сверьте
контракт, сохраните вход и ожидание, затем разберите минимальное исправление.
Не подменяйте заключительный вопрос демонстрацией всех готовых ответов.

## После занятия

Раздайте инструкторские материалы после самостоятельной работы. Предложите
сравнить свои сценарии с полным набором и объяснить различия. Домашнее продолжение:
придумать ещё одну осмысленную мутацию, предсказать красный тест, проверить прогноз
и обязательно восстановить код. Автоматический инструмент мутаций для этого
практикума устанавливать не требуется.
