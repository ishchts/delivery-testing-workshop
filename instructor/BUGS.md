# Карта восьми намеренных ошибок

Только для ведущего. Все имена ниже — реальные тесты из
`test/regressions.test.js`. Пример отдельного запуска против студенческой версии:

```sh
npm run test:student -- -t 'B1:'
```

Во всех восьми запусках исходный вариант красный, исправленный — зелёный.
Под «входом» ниже подразумеваются остальные поля по умолчанию, если они не указаны.

| ID | Тест-свидетель | Вход | Ожидание | Исходное поведение |
| --- | --- | --- | --- | --- |
| B1 | `B1: стандартная доставка при сумме ровно 3000 бесплатна` | `total: 3000` | `0` | `350` |
| B2 | `B2: Premium сам по себе даёт бесплатную стандартную доставку` | `total: 1000, isPremium: true` | `0` | `350` |
| B3 | `B3: промокод в нижнем регистре не даёт бесплатную доставку` | `total: 1000, promoCode: 'freeship'` | `350` | `0` |
| B4 | `B4: большой заказ с промокодом и Premium не удешевляет экспресс` | `total: 5000, isPremium: true, deliveryType: 'express', promoCode: 'FREESHIP'` | `700` | `0` |
| B5 | `B5: нулевая сумма допустима` | `total: 0` | `350` | `TypeError` |
| B6 | `B6: числовая строка вызывает TypeError` | `total: '1000'` | `TypeError` | `350` |
| B7 | `B7: отрицательная сумма вызывает RangeError` | `total: -1` | `RangeError` | `TypeError` |
| B8 | `B8: неизвестная доставка вызывает RangeError` | `total: 1000, deliveryType: 'pickup'` | `RangeError` | `350` |

## B1. Порог проверен без включения границы

В коде стоит `total > 3000`, хотя правило говорит «от 3000 включительно».
Реалистичная причина — пропущенный знак равенства при переводе требования в условие.
Исправление: `total >= 3000`. Тест на 5000 проходит при обоих операторах,
поэтому нужен сам порог. В полной таблице есть также значения по обе его стороны
и дробные суммы: шаг входных данных не ограничен целыми рублями.

## B2. Boolean сравнивается со строкой

`isPremium === 'true'` ожидает строковое представление, типичное для данных формы
или внешнего API, а контракт функции требует boolean. Выражение `true === 'true'`
ложно. Исправление: `isPremium === true`.
Для теста берём сумму ниже порога и убираем промокод: другая льгота не должна
скрыть неисправность Premium. Два исходных теста используют `false`.

## B3. Промокод необоснованно нормализуется

`promoCode?.toUpperCase()` принимает разные регистры, хотя договорённость требует
точного совпадения. Такая «удобная» нормализация меняет бизнес-правило.
Исправление: `promoCode === 'FREESHIP'`. Нужны и положительный пример с точным кодом,
и отрицательные примеры с другим регистром. Иначе удаление поддержки промокода
вообще может незаметно сделать один отрицательный тест зелёным.

## B4. Льготы срабатывают раньше ветки экспресса

Ранний `return 0` по сумме или промокоду не даёт дойти до проверки `'express'`.
Исправление: после валидации входа сначала обработать экспресс с `return 700`,
а затем льготы стандартной доставки. Тест-свидетель использует 5000, чтобы ошибка
B1 на точном пороге и ошибка B2 не мешали увидеть неверный приоритет.
Полная матрица проверяет каждое сочетание четырёх сумм, двух Premium-статусов и
трёх промокодов: 24 отдельных теста. Неверная сумма всё равно должна вызывать
исключение, даже для экспресса и клиента со всеми льготами.

## B5. Ноль ошибочно считается отсутствующей суммой

`!total` смешивает отсутствие значения и допустимый `0`: оба дают truthy-результат
отрицания. Исправление: убрать проверку на истинность, явно проверить тип и
конечность числа. Положительные суммы в двух стартовых примерах проблему не показывают.
Объясните, что `0` не означает отсутствие заказа по условиям этой задачи.

## B6. Проверяется преобразованное значение вместо входного

`Number.isFinite(Number(total))` сначала преобразует строку в число и тем самым
пропускает неверный тип. Аналогично могут пройти `true` и некоторые массивы.
Исправление: `typeof total !== 'number' || !Number.isFinite(total)`.
`Number.isFinite` не приводит типы; явный `typeof` оставлен для читаемости начинающими.
Проверка B5 и проверка B6 относятся к одной строке, но это две разные ошибки:
удаление `!total` не запрещает числовые строки, а удаление `Number(...)` не разрешает ноль.

## B7. Выбран неверный класс исключения

Отрицательное число отклоняется, но код выбрасывает `TypeError` вместо `RangeError`.
Тип корректен, нарушен разрешённый диапазон. Исправление: заменить конструктор ошибки.
Проверка только `.toThrow()` эту ошибку пропустит; `.toThrow(RangeError)` её обнаружит.
В `expect` передаётся `() => calculateDelivery(...)`, чтобы исключение перехватил Vitest.
`NaN` и бесконечности по контракту дают `TypeError`; проверка конечности идёт раньше диапазона.

## B8. Неизвестный способ превращается в стандартную доставку

Любое значение, кроме `'express'`, попадает в запасной `return 350`, а при большой
сумме может ещё раньше вернуть 0. Так опечатка в способе доставки становится
допустимым заказом. Исправление: до расчёта проверить два разрешённых значения
и иначе выбросить `RangeError`. Проверка только «обычного заказа без скидок»
недостаточна, если валидацию поставят после раннего `return 0`: в полном наборе
есть неизвестная доставка при каждом основании для льготы.
Пропущенный `deliveryType` и явный `undefined` используют документированное значение
`'standard'`; это не неизвестные способы. `null` значением по умолчанию не заменяется.

## Как убедиться, что это восемь отдельных дефектов

Мысленно верните одну ошибку в исправленную реализацию. Её тест-свидетель
должен стать красным, даже если остальные семь уже исправлены.
Технический прогон такой проверки записан в `../VERIFICATION.md`.
Число красных проверок полного набора больше восьми: несколько сценариев могут
обнаруживать один дефект, а некоторые падения имеют сразу несколько причин.

Зелёный полный набор означает согласие с проверенными примерами контракта.
Он не доказывает отсутствие всех возможных ошибок.
