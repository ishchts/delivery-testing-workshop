# Практика: какие сценарии мы забыли?

Не нужно угадать все ошибки сразу. Важнее уметь объяснить, какое требование
проверяет каждый ваш тест. Работайте в парах: один предлагает сценарий,
другой пытается найти в нём неоднозначность; затем поменяйтесь ролями.

## 1. Два зелёных примера

Запустите стартовые тесты. Для каждого назовите проверенное правило и предпосылки.
Какие части требований эти примеры вообще не затрагивают?
Можно ли по двум успешным результатам сделать вывод обо всех входных данных?

## 2. Сначала сценарии, затем код

Не читая реализацию, заполните хотя бы шесть строк. Ожидаемый результат берите
из README, а не из текущего поведения функции. Для исключения запишите его класс.

| Правило | total | isPremium | deliveryType | promoCode | Ожидаемый результат | Почему этот случай нужен |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |
| | | | | | | |
| | | | | | | |
| | | | | | | |
| | | | | | | |
| | | | | | | |

Вопросы для обсуждения:

- На какие группы можно разделить допустимые и недопустимые суммы?
- Где по требованиям меняется результат? Какие соседние значения стоит взять?
- Как проверить каждое основание для скидки отдельно?
- Какое правило важнее при одновременном выполнении нескольких условий?
- Что должно происходить при отсутствующем или неожиданном значении?
- Какие сочетания параметров могут показать то, чего не видно при проверке одного поля?

## 3. Найдите первое противоречие

Выберите сценарий, которого нет в стартовых тестах. До запуска вслух назовите
ожидаемый результат. Напишите один тест и прочитайте сообщение о падении.

Если тест красный, запишите:

| Входные данные | Ожидание по правилу | Фактический результат | Гипотеза о причине |
| --- | --- | --- | --- |
| | | | |

Только теперь откройте реализацию. Внесите минимальное исправление и запустите
все тесты. Если тест сразу зелёный, объясните, какое поведение он всё же защищает,
и выберите следующий сценарий. Не меняйте ожидание только ради зелёного результата.

## 4. Проверьте сочетания и ошибки входа

Добавляйте проверки по одной. Убедитесь, что тест не проходит благодаря другой
льготе, случайно включённой во входные данные. При проверке исключения
передавайте вызов функции в `expect` через функцию-обёртку и проверяйте класс ошибки.

Обсудите с соседней парой: действительно ли ваш тест отличит верную реализацию
от вашей гипотезы об ошибочной? Предложите друг другу ещё по одному сценарию.

## 5. Обобщите через test.each()

Найдите несколько проверок с одинаковыми действиями и разными данными.
Преобразуйте их в `test.each()`. Сначала сами предложите строки таблицы,
включая ожидаемые результаты. Оставьте в названиях данные, чтобы было понятно,
какая именно строка упала. Не объединяйте разные действия в одну громоздкую таблицу.

## 6. Проверьте силу тестов

На уже исправленном коде вместе с ведущим измените одно условие.
Перед запуском предположите, какие проверки заметят изменение.
Запустите сначала стартовые тесты, затем свой полный набор.
Верните правильное условие и убедитесь, что тесты снова зелёные.

Если изменение осталось незамеченным, какой сценарий нужно добавить?
Всегда ли выжившее изменение означает ошибку в тестах?

## Критерии готовности

- Каждый добавленный сценарий связан с конкретным бизнес-правилом.
- Для каждой исправленной ошибки сохранён тест, который падал до исправления.
- Проверены обычные случаи, границы, недопустимые значения и сочетания условий.
- Параметризованные проверки читаются без объяснения автора.
- После исправлений весь ваш набор зелёный; намеренное изменение обнаруживается.

В конце каждый участник предлагает один сценарий, который не показывал ведущий.
